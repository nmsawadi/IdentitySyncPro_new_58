# دليل محرّك القواعد ودورة الحياة — IdentitySyncPro

> **الغرض:** مرجع دائم لكيفية عمل قواعد المحرك (الربط) وقواعد دورة الحياة، وكيف تطبّقها في أي جهة/مشروع.
> **مبنيّ على الكود الفعلي:** `MappingEngine.cs` · `LifecycleEngine.cs` · `RulesEngineService.cs` ونماذج القواعد.
> **آخر تحديث:** 2026-07-25

---

## 0. العائلتان — لا تخلط بينهما

في النظام **عائلتان من القواعد** لهما وظيفتان مختلفتان تماماً:

| العائلة | متى تعمل؟ | ماذا تقرّر؟ | الملف |
|---|---|---|---|
| **قواعد المحرك** (Mapping) | وقت المزامنة، لكل سجل | *قيم* سمات AD، و*أي OU* يُنشأ فيه الحساب، و*أي مجموعات* | `MappingEngine.cs` |
| **قواعد دورة الحياة** (Lifecycle) | في خط الأنابيب الثلاثي | *ماذا يحدث للحساب* عند تغيّر حالته (نقل/أرشفة/مجموعات) | `LifecycleEngine.cs` |

- قاعدة المحرك تجيب: «الموظف رقم 5 — ما بريده وأي OU؟».
- قاعدة دورة الحياة تجيب: «الموظف رقم 5 صارت حالته 7 (متخرّج) — انقله للأرشيف وانزع مجموعاته».

## 1. قواعد المحرك (Mapping Rules)

ثلاثة أنواع، تشترك في **محرّك شرط واحد** ومجموعة **عوامل** واحدة.

### 1.1 عوامل الشرط (Operators) — الأساس المشترك

كل قاعدة لها: `ConditionField` (اسم عمود المصدر) · `ConditionOperator` · `ConditionValue`.
| العامل | المعنى | قواعد المحرك<br>(ربط/OU/مجموعات) | قواعد دورة الحياة |
|---|---|---|---|
| `==` | يساوي (غير حسّاس لحالة الأحرف) | ✅ | ✅ |
| `!=` | لا يساوي | ✅ | ✅ |
| `in` | ضمن قائمة مفصولة بفواصل (`4,5,6`) | ✅ | ✅ |
| `not_in` | ليس ضمن القائمة | ✅ | ✅ |
| `gt` / `lt` | أكبر / أصغر (رقمي) | ✅ | ❌ **يُطابق دائماً** |

> ⚠️ **فخّ دقيق:** `gt`/`lt` منفّذان في `MappingEngine.EvaluateSimpleCondition` (قواعد الربط وOU والمجموعات)، لكن `LifecycleEngine.EvaluateCondition` تنتهي بـ `_ => true` — فأي عامل غير الأربعة الأولى في **قاعدة دورة حياة** يُطابق كل هوية بصمت. استخدم `gt`/`lt` في قواعد المحرك فقط.

> ⚠️ **درس `STATUS_CODE` مقابل `STATUSE_CODE`:** `ConditionField` يجب أن يطابق اسم العمود الحقيقي. عمود غير موجود ← القيمة `null` ← لا مطابقة **بصمت** (قتلَ هذا 10 قواعد عبر 111,465 هوية). النظام الآن يضيف اسماً قانونياً `STATUS_CODE` عبر `BuildRuleAttributes`، والبحث غير حسّاس لحالة الأحرف — لكن ابقِ الوعي قائماً.

### 1.2 قواعد ربط السمات + محرّك التحويلات (Transforms)

كل قاعدة ربط: «خذ عمود المصدر، طبّق تحويلاً، ضعه في سمة AD». التحويلات **المنفّذة فعلاً** في `ApplyTransform`:

| التحويل | ما يفعله | إدخال | ناتج |
|---|---|---|---|
| *(فارغ)* | نسخ كما هو | `Ali` | `Ali` |
| `ToUpper` / `ToLower` | حالة الأحرف | `ali` | `ALI` |
| `Trim` | إزالة الفراغات | `" ali "` | `ali` |
| `Format:{0}@corp.com` | قالب بقيمة واحدة | `a.ali` | `a.ali@corp.com` |
| `Concat:{FIRST} {LAST}` | يدمج عدّة أعمدة مصدر | `FIRST=Ali,LAST=Saad` | `Ali Saad` |
| `Map:1=Riyadh,2=Jeddah` | جدول ترجمة | `2` | `Jeddah` |
| `Static:Employee` | ثابت يتجاهل المصدر | أي شيء | `Employee` |
| `Truncate:4` | يقصّ الطول | `Mohammed` | `Moha` |
| `GetInitials` | إن طال (>4) يأخذ أول حرف | `Mohammed` | `M` (و`Ali`→`Ali`) |

**مثال — بريد الموظف:**
```
SourceColumn = EMP_LOGIN  →  TargetAttribute = mail
Transform    = Format:{0}@corp.com
```
`EMP_LOGIN=a.saad` ينتج `mail = a.saad@corp.com`.

**مثال — اسم معروض من عمودين (Concat يقرأ كامل السجل لا عمود المصدر وحده):**
```
SourceColumn    = FIRST_NAME
Transform       = Concat:{FIRST_NAME} {FATHER_NAME} {FAMILY_NAME}
TargetAttribute = displayName
```

### 1.2-ب توليد اسم المستخدم من الأحرف — `Username:` (2026-07-25)

للجهات التي اسم المستخدم فيها مشتقّ من **الاسم** لا من رقم. الصياغة:

```
Username:<القالب>[|خيار][|خيار]
```

**العناصر النائبة:** `{COLUMN}` = العمود كاملاً · `{COLUMN:N}` = أول N حرفاً.
النص الحرفي بين العناصر يُحفظ (نقاط، شرطات، شرطات سفلية).

**الخيارات:** `lower` (افتراضي) · `upper` · `preserve` · `max:N` (افتراضي 20 = حدّ AD).

**أمثلة** على `FIRST_NAME=Mohammed` · `SECOND_NAME=ali` · `LAST_NAME=al hareth`:

| القالب | الناتج |
|---|---|
| `{FIRST_NAME:1}{SECOND_NAME:1}{LAST_NAME}` | `maalhareth` |
| `{FIRST_NAME}.{LAST_NAME}` | `mohammed.alhareth` |
| `{FIRST_NAME:1}{LAST_NAME}` | `malhareth` |
| `{LAST_NAME}{FIRST_NAME:1}` | `alharethm` |
| `{FIRST_NAME}_{EMP_NO}` | `mohammed_4471` |
| `{FIRST_NAME:1}{SECOND_NAME:1}{LAST_NAME}\|upper` | `MAALHARETH` |

**سلوك مقصود:** كل عمود يُنظَّف (حذف الفراغات والتشكيل) **قبل** أخذ أول N حرفاً — فـ `{LAST_NAME:3}` من «al hareth» = `alh` لا `al `. ثم تُحذف كل الرموز غير المسموحة في `sAMAccountName`، ويُقصّ الناتج إلى 20 حرفاً.

**تكرار الاسم:** شخصان بنفس الاسم يولّدان نفس القيمة. عند الإنشاء يفحص النظام التوفّر ويضيف رقماً: `maalhareth` ← `maalhareth2`. قابل للضبط لكل جهة:
`UsernameCollisionFormat` (افتراضي `{base}{n}`) · `UsernameCollisionStart` (2) · `UsernameCollisionMaxAttempts` (20). القاعدة تقصّ الأساس ليبقى الناتج داخل حدّ الـ20.

### 1.2-ج مفتاح المطابقة — `ADMatchAttribute` (2026-07-25)

**المشكلة:** إن كان اسم المستخدم مشتقاً من الاسم، فهو **ليس مفتاحاً ثابتاً**. تصحيح إملائي أو تغيّر اسم عائلة يولّد اسماً مختلفاً ← النظام لا يجد الحساب ← **يُنشئ حساباً مكرّراً** في كل مزامنة، بصمت.

**الحل:** المطابقة بسمة ثابتة تحمل الرقم الوظيفي.

| الإعداد | المعنى |
|---|---|
| `ADMatchAttribute` | سمة AD الحاملة للمفتاح (مثل `extensionAttribute2`). **فارغ = المطابقة بـ `sAMAccountName`** (السلوك الأصلي) |
| `ADMatchSourceColumn` | عمود المصدر الذي تُطابق قيمته. فارغ = `SourceKeyColumn` |

**كيف يعمل:**
1. يبحث عن حساب بـ `extensionAttribute2 = الرقم الوظيفي`.
2. **وُجد** → يستخدم `sAMAccountName` الموجود **كما هو** — لا إعادة تسمية، ولا حساب مكرّر.
3. **لم يوجد** → هوية جديدة: يولّد الاسم، يفحص توفّره (ويضيف رقماً عند الحاجة)، ثم **يبصم** الرقم الوظيفي في `extensionAttribute2` عند الإنشاء.

> ⚠️ **الخطوة 3 هي التي تُغلق الحلقة.** لو لم يُبصَم الرقم عند الإنشاء، لن تجده المزامنة التالية وستُنشئ حساباً ثانياً — وهكذا كل تشغيلة.

**حراسات ضد الفشل الصامت:**
- **مطابقة غامضة** (حسابان بنفس الرقم) → يُرفض السجل ويُسجَّل `Skipped` بالسبب، **لا يُختار أحدهما** (اختيار أحدهما يكتب هوية شخص على حساب آخر في كل مزامنة).
- **فشل قراءة AD** → استثناء صريح، **لا يُفسَّر كـ«الحساب غير موجود»** (وإلا لأنشأ حساباً مكرّراً).
- **عمود المطابقة فارغ** → يُرفض السجل (لا يمكن التمييز بين «شخص جديد» و«شخص تغيّر اسمه»).

### 1.2-د اختيار مفتاح المطابقة — أول قرار في أي تركيب جديد

> **لماذا هذا القسم أولاً:** خطأ هذا القرار لا يظهر عند الإعداد، بل **بعد أول مزامنة** — على شكل حسابات مكرّرة. وتصحيحه بعدها يتطلّب دمج حسابات في AD يدوياً.

**القاعدة الفاصلة** ليست «هل المصدر يحوي اسم المستخدم؟» بل:

> **هل يمكن أن تتغيّر هذه القيمة لنفس الشخص؟**

ما يجعل المطابقة بـ`sAMAccountName` آمنة عند الطلاب ليس أن الرقم يأتي من المصدر، بل أن **رقم الطالب لا يتغيّر**. أما عمود `LOGIN_NAME` في نظام شؤون الموظفين فهو حقل نصّي **يحرّره موظف** (تصحيح إملائي، تغيّر اسم عائلة، تعديل سياسة) — وأي تغيير فيه يجعل النظام يبحث عن الاسم الجديد فلا يجده فيُنشئ حساباً مكرّراً.

| ما يوفّره المصدر | الربط | لماذا |
|---|---|---|
| **رقم ثابت فقط** (الطلاب) | `sAMAccountName` — بلا `ADMatchAttribute` | الاسم مشتقّ من رقم لا يتغيّر |
| **اسم مستخدم مُولَّد آلياً ومقفل** | `sAMAccountName` — **شبيه بالطلاب تماماً** ✅ | القيمة ثابتة فعلياً |
| **اسم مستخدم قابل للتعديل** (الشائع) | `ADMatchAttribute` + الرقم الوظيفي | الاسم للعرض، والرقم للمطابقة |
| **لا رقم ثابت إطلاقاً** | ⛔ غير آمن بنيوياً | لا مفتاح يُطابق به |

#### الحالة الوسطى — المصدر يحوي الاسم والرقم معاً

أفضل تركيبة عملياً، ومدعومة بالإعداد وحده:

```
ربط الحقول:   LOGIN_NAME → sAMAccountName  [معرّف] + [مطلوب]
              (بلا تحويل Username: — الاسم جاهز من المصدر)

هوية الحساب:  ADMatchAttribute    = extensionAttribute2
              ADMatchSourceColumn = EMP_NO
```

- حساب **جديد** → يأخذ اسم المستخدم من شؤون الموظفين كما هو.
- حساب **قائم** → يُوجَد بالرقم الوظيفي، ويُستخدم `sAMAccountName` الموجود كما هو.
- تعديل الاسم في HR لاحقاً → **لا حساب مكرّر**.

فتحصل على تسمية المؤسسة وأمان المفتاح الثابت معاً.

#### مأخذان

**1. النظام لا يعيد التسمية إطلاقاً.** `UpdateDynamicAsync` تتخطّى `sAMAccountName` صراحةً. فتعديل الاسم في HR لموظف قائم **لا ينتقل إلى AD** ويفترقان في هذا الحقل. اختيار أمان مقصود — إعادة تسمية `sAMAccountName` تمسّ مسارات الملفات الشخصية وتذاكر Kerberos وتُربك المستخدم.

**2. علّم عمود اسم المستخدم «مطلوب».** لو جاء فارغاً، تُرجع `GetIdentifier` قيمة `null` فيسقط النظام على **الرقم** كاسم للحساب — فتحصل على حساب اسمه `4471` وسط حسابات بأسماء أشخاص، بلا خطأ. تعليمه «مطلوب» يجعل السجل يُسجَّل `Skipped` بسببه الصريح بدلاً من ذلك.

### 1.2-هـ سياسة إنشاء الحسابات — `AccountCreationMode` (2026-07-25)

قبل هذا الإعداد كان الإنشاء **غير مشروط**: أي هوية في المصدر بلا حساب في AD يُنشأ لها حساب تلقائياً. لجهة لا تُدار حساباتها من هذا النظام، كانت أول مزامنة تُنشئ حساباً لكل سجل في الـView.

| السياسة | السلوك |
|---|---|
| `Always` (افتراضي) | السلوك الأصلي — كل هوية بلا حساب يُنشأ لها |
| `Never` | لا يُنشأ أي حساب. قواعد الربط ودورة الحياة تُطبَّق على **الحسابات القائمة فقط** |
| `Conditional` | يُنشأ فقط لمن يحقّق الشرط (`AccountCreationCondition*`) — مثل «الموظفون النشطون فقط» |

**فارغ = `Always`** — الجهات المُعدّة قبل وجود هذا الإعداد لا يتغيّر سلوكها (وتحويلها صامتاً إلى «لا تُنشئ» يوقف التزويد بلا أي خطأ).

**الرفض عند الشك** — ثلاث حالات تُرفض فيها الإنشاء بدل تخمينه:
- **شرط ناقص** (عمود أو عامل أو قيمة فارغة) → لا يُنشأ أحد. `EvaluateSimpleCondition` تُرجع `true` عند غياب العامل، فالشرط نصف المكتمل كان **سيُنشئ الجميع** — عكس المقصود تماماً.
- **عمود غير موجود في المصدر** → يُرفض، والسبب **يذكر اسم العمود** (صنف خطأ `STATUS_CODE`/`STATUSE_CODE`).
- **قيمة سياسة غير معروفة** (تعديل يدوي في قاعدة البيانات) → تُرفض ولا تُخمَّن.

> **الملخّص في نهاية التشغيلة:** «لا تُنشئ» تُنتج سطر تخطٍّ لكل هوية — وهو الشكل الذي يمرّره المشغّل بعينه. لذلك يُطبع `Provisioning withheld for N identities` مع تفصيل الأسباب وأعدادها، **حتى لو انتهت التشغيلة جزئياً**.

### 1.3 قواعد وضع الوحدة التنظيمية (OU Rules)

`TenantOURule` تقرّر *أين* يُنشأ الحساب: شرط اختياري + قالب `OUTemplate` بعناصر نائبة + `ValueMappings` (جدول ترجمة). **أول قاعدة يتحقّق شرطها تفوز** (ترتيب `Priority` تصاعدي).

**مثال — توزيع حسب القسم:**
```
Priority       = 10
ConditionField = EMP_STATUS , Operator = == , Value = 1
OUTemplate     = OU={DEPT},OU=Employees,{BaseDN}
ValueMappings  = {"DEPT":{"10":"Finance","20":"IT","30":"HR"}}
```
- `{BaseDN}` → DN الجهة (`DC=corp,DC=local`).
- `DEPT=20` → `OU=IT,OU=Employees,DC=corp,DC=local`.
- عنصر نائب بلا قيمة → يُستبدل بـ `DEFAULT` **مع تحذير** (وغالباً يُفشل إنشاء الحساب — درس `OU=DEFAULT,OU=DEFAULT`).
- بلا قاعدة متطابقة → المرتجع `baseDN` نفسه.

### 1.4 قواعد المجموعات (Group Rules)

`TenantGroupRule` — وضعان:

**افتراضية للجميع:**
```
GroupName = All-Staff , IsDefault = true
```
**مشروطة:**
```
GroupName = License-IT , ConditionField = DEPT , Operator = == , Value = 20
```
- يقبل `GroupDN` كاملاً أو `GroupName` (يُحلّ وقت التشغيل).
- **كل** القواعد المتطابقة تُجمع (ليس «أول من يفوز»).

## 2. قواعد دورة الحياة (Lifecycle Rules)

### 2.1 تشريح القاعدة

```
① الهوية:  Name , Enabled , Priority (الأصغر أولاً)
② المُطلِق: TriggerType
③ الشرط:   ConditionField / ConditionOperator / ConditionValue
④ الفعل:   ActionType / ActionValue
⑤ المهلة:  GracePeriodDays
```

### 2.2 المُطلِقات (TriggerType) — نقطة الخلط الكبرى

| TriggerType | يُحمَّل؟ | الدور |
|---|---|---|
| `OnImport` | ✅ | يغيّر **الحالة** في الـMetaverse |
| `OnExport` | ✅ | ينفّذ **فعلاً في AD** (نقل، مجموعات) |
| `OnSchedule` | ❌ | مذكور، لا يُستعلم عنه → **لا يعمل** |
| `OnStateChange` | ❌ | مذكور، لا يُستعلم عنه → **لا يعمل** |

> القاعدة: `OnImport` لتغيير الحالة، `OnExport` لتنفيذ النقل/المجموعات. لا تعتمد على `OnSchedule`/`OnStateChange`.

### 2.3 الأفعال (ActionType) — المنفّذ مقابل المعلَن

| ActionType | منفّذ؟ | يفعل | ActionValue |
|---|---|---|---|
| `SetState` | ✅ | يغيّر حالة دورة الحياة | `Active`/`Suspended`/`Deprovisioned` |
| `MoveOU` | ✅ | ينقل الحساب | مسار OU، يدعم `{BaseDN}` |
| `Reactivate` | ✅ | Active + تفعيل + نقل اختياري | OU الوجهة |
| `Deprovision` | ✅ | Suspended + نقل + نزع كل المجموعات — **بلا تعطيل** (Safe Sync) | OU الأرشيف |
| `AddGroups` | ✅ | يضيف لمجموعات | أسماء، أو `{GroupRules}` |
| `RemoveGroups` | ✅ | ينزع من محدّدة، أو الكل إن فرغ | أسماء أو فارغ=الكل |
| `DisableAD` / `EnableAD` | ❌ | مذكور، **لا `case` له** — بلا أثر | — |
| `SendSMS` | ❌ | مذكور، غير منفّذ | — |

> ⚠️ ثلاثة أفعال معلَنة وغير منفّذة (`DisableAD`, `EnableAD`, `SendSMS`) — قاعدة بأحدها تُطابق شرطها ثم **لا تفعل شيئاً بصمت**.

**العنصران النائبان:**
- `{BaseDN}` في `ActionValue` للنقل → DN الجهة.
- `{GroupRules}` في `AddGroups` → «استنتج المجموعات من قواعد المجموعات لهذه الهوية». يحلّ قيد الشرط الواحد (لا يمكن التعبير عن «نشط **و** في هذه المدينة»). تجنّب قاعدة AddGroups لكل موقع.

### 2.4 الأولوية والمهلة

- **Priority:** الأصغر يُقيَّم أولاً. كل القواعد تُفحص؛ آخر `SetState` تطابق هي التي تبقى.
- **GracePeriodDays:** إن > 0، لا يُنفَّذ الفعل إلا بعد N يوماً على `StateChangedDate`.

### 2.5 خط الأنابيب الثلاثي

```
① Import     → المصدر إلى Metaverse، حساب البصمة، تعليم NeedsRuleEval
② ApplyRules → قواعد OnImport تغيّر الحالة
③ Export     → قواعد OnExport (+OnImport في الدفعي) تنفّذ في AD
```

**فرق المسارات (مرجع دائم):**

| | من ينفّذ `MoveOU`؟ | القواعد المحمَّلة في التصدير |
|---|---|---|
| **الكاملة/الدفعية** | المرحلة 2 تسجّل النية، `BulkExport` تنفّذ | `OnExport` **+** `OnImport` |
| **الفردية/الدلتا** | `ApplyLifecycleRules` تنفّذ مباشرة | `OnExport` **فقط** |

> ⚠️ لا «توحّد المسارين» بتحميل `OnImport` في التصدير الفردي — **يُكرّر كل نقل**. يحميه اختبار `FullPipeline_MovesTheAccountExactlyOnce`.

**السياسة الافتراضية** (بلا قاعدة مطابقة): `Pending` → `Active`، وما عداها بلا تغيير.

### 2.6 مثال كامل (متخرّجون — الحالة 7)

```
① Name=GraduateSuspend , TriggerType=OnImport , Priority=10
   ConditionField=STATUS_CODE , == , 7
   ActionType=SetState , ActionValue=Deprovisioned

② Name=GraduateMove , TriggerType=OnExport , Priority=20
   ConditionField=STATUS_CODE , == , 7
   ActionType=MoveOU , ActionValue=OU=Graduates,OU=Archive,{BaseDN}

③ Name=GraduateStripGroups , TriggerType=OnExport , Priority=30
   ConditionField=STATUS_CODE , == , 7
   ActionType=RemoveGroups , ActionValue=  (فارغ = كل المجموعات)
```

> ⚠️ لا تستثنِ `Deprovisioned` من `BulkExport`، وإلا صار النقل للأرشيف **مستحيلاً بنيوياً**. الشرط الصحيح: `LastExportDate == null || StateChangedDate > LastExportDate`.

## 3. جدول القرار — حالة المصدر إلى قواعدها المتوقّعة

مثال مبنيّ على أرقام الترحيل الفعلي (91,504 حساباً، صفر فشل):

| رمز الحالة | المعنى | OnImport (الحالة) | OnExport (AD) | العدد الفعلي |
|---|---|---|---|---|
| **1** | نشط | — (يبقى Active افتراضياً) | `AddGroups {GroupRules}` | — |
| **7** | متخرّج | `SetState=Deprovisioned` | `MoveOU=OU=Graduates,{BaseDN}` + `RemoveGroups` | 47,526 |
| **10** | منسحب | `Deprovision` (Suspended) | `MoveOU=OU=Resigned,{BaseDN}` | 21,132 |
| **4,5,6,9** | حالات نقل | `SetState`/`MoveOU` حسب الرمز | نقل OU مطابق | 22,789 |
| **2,3,11,12** | بلا قاعدة SetState | — (تبقى Active بقرار إداري) | تنقلها `not_in 1,7` | 57 |

> **تحذير الرموز غير المغطّاة:** كل رمز حالة بلا قاعدة مطابقة يُسجَّل باسمه وعدده — راجعه قبل كل مرحلة.

## 4. كيف تطبّقها في أي مشروع (مثال: الموظفون)

### الخطوة 1 — الجهة والمصدر
```
المصدر: HR.V_EMPLOYEES  (أعمدته كما هي)
عمود المعرّف:   EMP_NO       (رقمي، فريد)  ← مفتاح التتبّع الداخلي
عمود الحالة:    EMP_STATUS   (رقمي)
اتصال AD: خاص بالجهة (إلزامي، لا رجوع لـ appsettings)
```

> **مهم:** التتبّع الداخلي (`SyncStates` / `MetaverseEntries` / السجل) يستخدم `EMP_NO` دائماً — **لا** اسم المستخدم. اسم المستخدم قيمة في AD فقط.

### الخطوة 1-ب — مفتاح المطابقة (لهذه الجهة تحديداً)
```
ADMatchAttribute    = extensionAttribute2
ADMatchSourceColumn = EMP_NO        (أو فارغ = يستخدم عمود المعرّف نفسه)
```

### الخطوة 2 — قواعد المحرك (الربط)
```
FIRST_NAME → sAMAccountName  [معرّف]
             Transform=Username:{FIRST_NAME:1}{SECOND_NAME:1}{LAST_NAME}
             ← Mohammed ali al hareth  ينتج  maalhareth

EMP_NO     → extensionAttribute2   Transform=(فارغ)   ← اختياري (يُبصَم تلقائياً)
EMP_LOGIN  → mail                  Transform=Format:{0}@corp.com
FIRST_NAME → displayName           Transform=Concat:{FIRST_NAME} {SECOND_NAME} {LAST_NAME}
DEPT       → department            Transform=Map:10=Finance,20=IT,30=HR

OU:      Priority=10 , EMP_STATUS==1
         OUTemplate=OU={DEPT},OU=Employees,{BaseDN}
         ValueMappings={"DEPT":{"10":"Finance","20":"IT","30":"HR"}}

مجموعات: All-Staff (IsDefault) · License-IT (DEPT==20)
```

> **لاحظ:** `Username:` يقرأ الأعمدة التي **يسمّيها القالب**، فعمود المصدر في قاعدة المعرّف لا يؤثّر على الناتج (اختره أي عمود اسم). وإن كانت كل أعمدة القالب فارغة فلا يُولَّد اسم ويُرفض السجل — بدل أن يُستخدم الرقم الوظيفي اسماً بصمت.

### الخطوة 3 — قواعد دورة الحياة
```
نشط (1):     لا SetState (يبقى Active) + OnExport/AddGroups={GroupRules}
مستقيل (10): OnImport/==10/Deprovision/OU=Resigned,OU=Archive,{BaseDN}
متخرّج (7):  OnImport/==7/SetState=Deprovisioned
             OnExport/==7/MoveOU=OU=Graduates,OU=Archive,{BaseDN}
جامعة:       not_in 1,7,10 → OU مراجعة (وراقب تحذير الرموز غير المغطّاة)
```

### الخطوة 4 — التطبيق والتحقّق
```
□ جرّب على 3–5 حسابات أولاً وتحقّق في AD بعينك
□ شغّل تجريبياً (dry-run) — تأكّد أنه لا يكتب ولا ينقل
□ طبّق مرحلة بمرحلة (رمز واحد كل مرة)
□ راقب أول دقائق: ارتفاع Failed = أوقف فوراً
□ لا معاملات SQL مفتوحة (BEGIN بلا COMMIT يشلّ المزامنة)
```

### الخطوة 5 — البصمتان المنفصلتان

| ما تريد إعادة تطبيقه | ما تُفرّغه |
|---|---|
| سمات AD (قواعد الربط) | `SyncStates.CurrentHash = ''` |
| قواعد دورة الحياة | `MetaverseEntries.NeedsRuleEval = 1` |
| إعادة التصدير بعد تغيّر حالة | `MetaverseEntries.LastExportDate = NULL` |

> تفريغ البصمات وحده **لا يُشغّل دورة الحياة** — شرط `SyncEngine` يقارن حقول `MetaverseEntries` لا `SyncStates`.

**استعلام تشغيل مرحلة واحدة:**
```sql
UPDATE MetaverseEntries SET NeedsRuleEval = 1, LastExportDate = NULL
WHERE TenantId = 1 AND SourceStatusCode = 7;
```

## 5. الخيط الجامع

كل القواعد تتبع نمطاً واحداً: **شرط بسيط (`Field Op Value`) ← فعل واحد**. القوة في التركيب (قواعد بأولويات)، والخطر في **الصمت**: اسم عمود خاطئ، أو عامل غير مدعوم، أو فعل غير منفّذ (`SendSMS`)، أو مُطلِق لا يُحمَّل (`OnSchedule`) — كلها **تُطابق أو تُتجاهَل بلا خطأ**. لذا القاعدة الأولى: **اختبر على عيّنة صغيرة وتحقّق بعينك في AD قبل أي دفعة**.
